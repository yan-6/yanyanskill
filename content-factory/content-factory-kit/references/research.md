# 阶段一 · 研究执行力规范

配套 `content-factory-kit` 支路 A。本份管**研究阶段**：查什么、怎么查、按什么结构写、
什么标准算合格才写回工作台。

研究是联网做的：页面只生成一张任务卡写进队列，真正的检索、核查、成文由领取任务的 agent 完成。

## 一、开工前三件确认

1. **对象是否真实存在**：先确认「目标键」在目标表里查得到，且标题不是测试残留。
   判断脏数据的特征：没有栏目、没有目标平台、没有资料、没有大纲，且选题库里同名记录已放弃。
2. **是否重复派发**：同一目标键在队列里常有多条（人会连点）。已有上一版结论时按**增量更新**做，
   不要重写全文。
3. **任务卡是否完整**：任务卡应含硬性约束与结构要求。缺失时按本规范的结构执行，
   并在结果摘要里注明「任务卡缺约束，按默认规范执行」。

对象是脏数据、或根本没研究对象时：**不虚构简报**。按硬约束输出
「无法研究 + 依据 + 处置建议」，用【待核实：xxx】标出缺口。

## 二、检索策略

- **源优先级**：一手来源（官方博客 / Release Notes / 官方文档 / 财报 / 论文 / 代码仓库与 PR）
  > 权威媒体 > 二手转述与聚合站。
  能用抓取工具直取原文时优先直取，**不要停在搜索结果摘要**。
- **时间窗**：AI 类选题默认只看最近 3 个月；行业分析放宽到 12 个月。
  任务卡给了时效窗口就以任务卡为准。
- **关键词**：中英文各给一组。技术类选题**英文关键词优先**（一手信息多为英文），
  术语用官方叫法而不是中文意译。
- **工具映射**（按可用性调整）：搜索找线索 → 抓取取原文 → 事实核查工具交叉验证 →
  资讯聚合看是否已有中文报道与热度。
- **只在第三方转述里出现的数据**（性能倍数、成本、份额、版本数量、issue 占比等）：
  一律**保留原文措辞**并标【待核实】，不得改写成确定结论。

## 三、产出结构（结构不合格不写回）

**研究摘要固定 8 段**，第 1 段是时效标注：

```
信息截止：YYYY-MM-DD（检索时间）
1. 背景：来龙去脉，为什么是现在发生
2. 核心事实：可核实的关键信息（时间、主体、数字、版本号）
   每条后面用「（来源：xxx）」标注出处；查不到出处的标【待核实：xxx】
3. 亮点与差异：真正新的地方是什么，和上一代或竞品比差异在哪
4. 不同观点：支持与质疑双方各自的理由
5. 值得讨论的问题：3–5 个有张力的开放问题
6. 可切入角度：3 个不同写法，各自适合的读者
7. 还需要补什么：接下来该去查的信息
8. 信息来源：本次实际用到的来源清单（标题 + 链接 + 类型），一行一条
```

其余产出沿用任务卡结构：内容大纲（每节小标题 + 核心观点 + 预计字数）、正文、制作方案。

**为什么固定 8 段**：不是为了好看。第 1 段的时效标注让下一篇知道这份资料什么时候过期；
第 8 段的来源清单让复核不用重查；第 4 段的「不同观点」防的是单方面结论；
第 7 段的「还需要补什么」让下一轮不重复劳动。少一段就少一个防错机制。

## 四、篇幅预算

| 产出 | 预算 |
|---|---|
| 研究摘要 | 800–1500 字（8 段齐全优先，不为凑字灌水） |
| 内容大纲 | 2500–3500 字为上限，超出即压缩小节数 |
| 正文 | **起稿按 ≤2400 字**，交付区间 1500–2500 字 |
| 制作方案 | 不限，但每张配图要说明用途与平台尺寸 |

正文超限返工是**高频问题**——按 ≤2400 字起稿可以省掉一轮返工。

## 五、写回契约

**不要绕过工作台的写回工具直连底层接口**：包装类型写错会静默丢值，你不一定收到报错。

- **单字段动作**（核查 / 研究 / 补来源 …）→ 单字段写回，落到「落点表.落点字段」。
- **一键成篇类** → 一次性写回 **研究摘要 / 内容大纲 / 正文 / 制作方案 + 状态**，
  **只写这几个字段**，不要顺手改标题。
- JSON 的键名必须与目标表字段名**完全一致**。写回输出里出现「跳过未知字段」= 键名写错了，要改。
- 长文本一律走「读文件传值」而不是命令行内联，避免转义问题。
- 写回前先只读试跑（`--dry`）看计划，确认无误再正式写。

字段名与表 ID 因工作台实例而异，**用你自己的表结构查**：
先取表清单 → 再取目标表的字段定义 → 确认字段存在且类型对得上，再写。

## 六、来源回流（重要，常被漏）

研究做完了但来源只留在正文里，下次要复核就得重查。所以**每次研究类任务完成后，
把实际用到的来源回写到「研究资料表」**。

来源文件结构：

```json
[{"名称": "来源标题", "类型": "官网", "链接": "https://…", "备注": "支撑了哪条结论"}]
```

- 写回工具一般已内置：按「内容ID + 链接」**去重**、非法类型归「其他」、缺名称的**跳过**、
  单次有**条数上限**（常见是 8 条）。
- 处理顺序是固定的：先按「内容ID + 链接」去重 → 再跳过缺名称的 → 最后按原顺序截取到上限。
  **能写几条 = 跳过之后还剩几条**，所以 10 条里若 2 条被跳过，仍会写满上限。
- 资料类型枚举（按你的表实际枚举走，常见为）：新闻链接 / 官网 / 代码仓库 / 公众号文章 /
  产品资料 / PDF / 图片 / 个人笔记 / 其他。
- **只回流真正读到并支撑了结论的来源**，不要把搜索列表整页倒进去。
- 回流失败不影响字段写回：**先写四段产出，再回流来源**；失败就在结果摘要里注明
  「来源未回流」+ 原因。

## 七、写回前验收清单

逐条核对，有一条不过就先修，不要带着问题写回：

1. 研究摘要 8 段齐全（含首行「信息截止」与末段「信息来源」）
2. 核心事实里每个数字 / 时间 / 版本号都能在「信息来源」里找到出处，或已标【待核实】
3. 没有编造的链接、引文、人物发言（链接必须真实打开过）
4. 第三方转述的数据没有被写成确定结论
5. 正文在 1500–2500 字区间
6. JSON 键名与表字段名完全一致，未出现「跳过未知字段」
7. 目标键在目标表里确实存在（脏数据要标记失败而不是硬写）
8. 状态推进正确：一键成篇 → 待发布；单字段动作不动状态
9. 来源已按去重规则回流（或已在结果摘要注明未回流原因）
10. 结果摘要里写清「查到了什么 / 哪些是待核实 / 落到哪个字段」

## 八、失败与降级处置

| 情况 | 处置 |
|---|---|
| 目标记录已删除 / 是测试残留 | 标失败 + 归档建议，不要写回（写回会把状态推到待发布） |
| 检索不到任何一手来源 | 标记完成 + 输出「无法研究 + 已尝试的检索路径 + 建议」，不要虚构 |
| 部分事实只有转述 | 标记完成 + 结论前标【待核实】，不算失败 |
| 工具报错 / 表不可达 | 标失败 + 原始错误摘要；不要改数据绕过 |
| 同一目标重复派发 | 只做一次，其余任务写「与 XXX 同源，已合并」后标记完成 |

**为什么慎用「失败」**：失败的条目每轮会被跳过且永久悬空。
所以只有在**不该产出内容**时才标失败；查不全但结论成立的情况走「完成」。

## 九、常见坑

- 上一轮的临时产物文件名不要复用，用带日期后缀的新名字，避免写到一半发现文件是旧的。
- 长文本用「读文件」方式传值；大 JSON 走命令行参数在部分 shell 下会静默失败。
- 队列列表里「共 N 条待处理」含待执行 / 执行中 / 失败，**N > 0 不等于有活干**，必须逐条看状态。
- 复核要全表 dump 时，输出路径必须带目录，直接给个文件名会报错。
- 字段是否真的存在，先取表结构核实，再决定要不要补。
