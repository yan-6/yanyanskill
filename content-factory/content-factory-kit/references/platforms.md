# 阶段三 · 多平台改写规范

配套 `content-factory-kit` 支路 A。一篇正文发到不同平台，**不是复制粘贴，也不是重写一遍**——
是「同一批事实，换一套讲法和包装」。

## 一、改写铁律：可以变的 / 不能变的

| 可以变 | 绝对不能变 |
|---|---|
| 标题（每个平台重写，不要共用） | 数字、时间、版本号、行数、金额 |
| 开头形态与篇幅 | 结论的方向（不能为了平台口味把「不推荐」写成「真香」） |
| 结构顺序与分节粒度 | 「（来源：xxx）」标注与「【待核实：xxx】」标记 |
| 语气强度（声道程度） | 代码、命令、专有名词与大小写 |
| 排版、标签、表情与配图 | 是否属于 A / B 声道的**根本选择** |
| 结尾互动方式 | 已声明的边界与局限（专业稿的「能力边界」不能在小红书版里消失） |

**最重要的一条**：一稿多投最大的风险是**某个平台版把结论写夸张了**。
平台口味只能改「怎么说」，不能改「是什么」。

如果某平台确实需要更轻的表达，就把结论**缩小范围**说
（「我自己用下来是这样」），而不是**放大程度**说（「效果爆炸」）。

## 二、声道与平台的关系

声道是**作者的声音**，不是平台的属性——同一篇 A 声道稿发到小红书，仍然是 A 声道，
只是排版更碎、开头更直接。

| 平台 | 通常声道 | 说明 |
|---|---|---|
| 掘金 / CSDN | A 为主 | 技术读者，克制理性；个人项目稿可用 B，但要有技术密度 |
| 微信公众号 | A / B 都常见 | 看题材定，正文可以完整保留原声道 |
| 小红书 | A / B 都可，但**表达要更短** | 短不等于卖萌；技术稿在小红书也要保持信息真实 |
| 视频号 / B站 / 抖音 | B 更容易起量 | 口播要像说话，但不能丢掉结论的限定条件 |

**禁止**：为了让内容「更适合平台」而整体换声道。
B 声道稿发到掘金，是**把口语收紧**，不是改成「综上所述」。

## 三、总流程

```
① 定平台读者与场景 → ② 该平台重写标题 → ③ 重排结构（开头形态由平台决定）
→ ④ 事实与结论对齐原稿 → ⑤ 补平台专属件（标签 / 摘要 / 首图文字 / 口播稿）
→ ⑥ 逐条过平台自查 → ⑦ 写回「制作方案」（追加，不要覆盖）
```

- **一次只处理一个平台**，不要在一段输出里混着写多个平台，容易串味。
- 每个平台版本开头都要**单独起笔**，不要从原稿第一段改几个词了事。
- 各平台版本的**核心结论句应保持一致**，方便复核有没有改跑偏。

## 四、平台卡片

> **关于字数与字段限制**：下面给的区间是**写作约定**（按读者耐心定），不是平台硬上限。
> 平台的字数 / 标题长度限制会调整，**发布前以平台当前提示为准**。
> 这里不写死具体上限值，避免过期误导。

### 微信公众号

| 项 | 约定 |
|---|---|
| 读者与场景 | 订阅关系，打开时有一段完整注意力；多为科技从业者与爱好者 |
| 声道 | A / B 都可，**保留原稿声道** |
| 标题 | 两段式；**留悬念、不剧透结论**；可用问句 |
| 摘要 | 独立成句，**不剧透结论**（摘要的作用是让人点进来） |
| 开头 | 前 3 句给钩子；长文场景，可以从一个具体场景或冲突起笔 |
| 结构 | 六拍完整；编号大节 + 口语化小标题；表格 / 代码 / 截图佐证 |
| 篇幅 | 1500–2500 字 |
| 排版 | 短段落、多小标题；重点句单独成行；图注写清「图：xxx」 |
| 结尾 | 总结回扣 + 互动引导（关键词回复 / 留言提问）+ 下期预告 |
| 转发语 | 朋友圈转发语，**第一人称**（「我把这套流程跑通了，踩的坑都写下来了」） |
| 禁忌 | 摘要里剧透结论；开头大段背景铺垫；结尾空泛升华 |

### 掘金 / 技术社区

| 项 | 约定 |
|---|---|
| 读者与场景 | 技术读者，带着「能不能用在我这儿」的问题来；对营销腔敏感 |
| 声道 | **A 为主**；个人项目稿可用 B，但必须有技术密度 |
| 标题 | 技术向、**不用情绪词**；给 3 个备选；可带技术关键词 |
| 开头 | **先给结论 + 适用场景**，再补背景；**不要悬念式开头**（技术读者没耐心） |
| 结构 | 环境 / 版本 / 成本前置声明 → 问题 → 方案 → 代码或步骤 → 结果数据 → 踩坑清单 → 边界 |
| 篇幅 | 2000–4000 字可接受；技术点讲透优先于控字数 |
| 代码与表格 | 代码块标语言；命令给完整可复制版本；对比用表格 |
| 标签 | ≤5 个，**精准优先**（框架名 / 语言名 好过「前端」） |
| 摘要 | 讲清解决了什么问题 |
| 结尾 | 边界声明 + 后续计划；可引导 issue / 讨论 |
| 禁忌 | 情绪化标题；只有结论没有环境声明；「我试了感觉不错」式无数值结论 |

### CSDN（长文归档）

| 项 | 约定 |
|---|---|
| 读者与场景 | 搜索流量为主，很多人是来查具体问题的；文章生命周期长 |
| 声道 | A 为主 |
| 标题 | 可带技术关键词，便于搜索命中；不必强行两段式 |
| 开头 | 直接给问题背景与结论，**搜索来的读者要立刻看到答案** |
| 结构 | 目录化（一、二、三 明确编号）；步骤可复现；代码完整 |
| 篇幅 | 不限，**宁长勿短**（归档属性，详细比精简有价值） |
| 排版 | 代码块 + 目录 + 关键步骤截图；版本号写清楚 |
| 结尾 | 参考链接 / 相关文章；少用互动引导 |
| 禁忌 | 排版花哨；把公众号文案原样搬过来（缺少可复现步骤） |

### 小红书

| 项 | 约定 |
|---|---|
| 读者与场景 | 碎片时间刷，**先看图再看字**；对「成果」的感知强于「原理」 |
| 声道 | A / B 都可，但**表达必须更短**；短 ≠ 卖萌 |
| 标题 | 短（一般 20 字内），真实语气，**不标题党**；可以用「结果前置」写法 |
| 首图文字 | 一句能看懂（首图承担大部分点击），越短越好 |
| 开头 | 第一句就给**结果或反差**（「我把 25 分钟的活压到 4 分钟了」） |
| 结构 | 单点为主：一个结论 + 1–2 个证据 + 可操作步骤；**不要塞进整篇文章** |
| 篇幅 | 正文 300–600 字；每段不超过 2 行 |
| 标签 | **混合大流量词 + 精准长尾词**（全用大词等于没用） |
| 表情 | 克制使用，做节奏断点而不是装饰 |
| 结尾 | 一句话互动引导（提问 / 求补充 / 下期想看的） |
| 禁忌 | **把严肃结论写成浮夸种草口吻**；为了平台口味放大效果；把长文的全部细节搬过来 |

### 视频号（竖版口播）

| 项 | 约定 |
|---|---|
| 读者与场景 | 微信生态内推送，边刷边听；**前 3 秒决定是否划走** |
| 声道 | B 更容易起量；口播要像说话 |
| 标题 / 首屏文案 | 短、有钩子；口播第一句就是标题感 |
| 开头 | **结论前置**，一句话说清「看完能得到什么」 |
| 结构 | 一个观点 + 一个证据 + 一个动作；不铺排多个论点 |
| 篇幅 | 60–120 秒稿（约 200–400 字口播文字） |
| 口播稿要求 | 能说出口：短句、少书面连接词、不用括号说明；标出分镜与画面提示 |
| 封面 | 文案短；**不含品牌元素**（见 `visual.md`） |
| 结尾 | 引导关注 / 留言；给下一期的钩子 |
| 禁忌 | 把正文朗读一遍；书面语长句；一上来讲背景 |

### B站（横版中长视频）

| 项 | 约定 |
|---|---|
| 读者与场景 | 主动搜索或推荐进入，容忍度高，**能接受技术细节** |
| 声道 | B 为主，可以有梗；但技术内容要有密度 |
| 标题 | 可长、可带梗，不强制两段式 |
| 开头 | 片头钩子（一个反差提问或一个翻车现场），10 秒内进正题 |
| 结构 | 分节清晰（配章节进度），可放完整演示 |
| 篇幅 | 3–10 分钟稿；比视频号能容纳更多论据 |
| 专属件 | 章节分节、演示步骤、结尾三连引导 |
| 结尾 | 三连引导 + 下期预告 |
| 禁忌 | 与视频号共用一版不调节奏；只有结论没有演示过程 |

### 抖音（极短）

| 项 | 约定 |
|---|---|
| 读者与场景 | 强推荐流，**前 3 秒定生死**，完播率优先 |
| 声道 | B |
| 标题 / 文案 | 极短；文案配合字幕 |
| 开头 | 前 3 秒**把结论或反差砸出来**，不要任何铺垫 |
| 结构 | 一个点讲完就结束；宁可短 |
| 篇幅 | 15–60 秒稿 |
| 专属件 | 前 3 秒钩子、字幕文案（逐句）、话题标签 |
| 结尾 | 一句话引导（关注 / 评论区见） |
| 禁忌 | 讲原理；句子超过 15 字；一条视频塞两个论点 |

## 五、写回契约

多平台类动作的落点统一是**共享的「制作方案」字段**（不是正文——原稿不会被覆盖）。

- **`写回是覆盖式的`**：如果制作方案里已经有封面方案、插图方案，
  再写多平台版本会**把它们顶掉**。
- 所以写回前先读一遍现有内容，用**追加式排版**写，不要只输出自己这一段。
- 长文本一律走「读文件传值」。

## 六、交付前自查

1. 每个平台版本**标题是单独写的**吗？不是原稿标题套用？
2. 开头是**按平台形态重起**的吗（公众号留悬念 / 掘金先结论+环境 / 小红书先给结果 / 视频口播先说结论）？
3. 数字、结论方向、来源标注、待核实标记，与原稿**逐条一致**？
4. 有没有为了平台口味把结论放大？**缩小范围可以，放大程度不行。**
5. 该平台的专属件都齐了吗（摘要 / 标签 / 首图文字 / 口播稿 / 三连引导）？
6. 字数在该平台区间内？
7. **制作方案里原有内容有没有被覆盖掉？**
8. 结果摘要里列清「生成了哪几个平台版本 / 各自字数 / 落在制作方案」。

## 七、常见坑

- **别用同一套开头改所有平台**。公众号和抖音的开头逻辑完全相反：
  公众号要留悬念不剧透，抖音要前 3 秒把结论砸出来。
- **标签不要凑数**。全用大词等于没用，要混合大流量词和精准长尾词。
- **短视频脚本不是正文朗读**。口播稿必须改写成能说出口的句子
  （不用书面连接词、句子更短），并标出分镜。
- **视频号 / B站 / 抖音的时长差异要显式处理**：同一篇内容给两个平台时，
  要说明各自要砍掉什么、节奏怎么调，不能只给一版让人自己剪。
- **「制作方案」是共享字段**，多平台任务最容易误伤封面 / 插图方案——写回前先读现有内容。
