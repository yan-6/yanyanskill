# 多平台改写 · 本机绑定层

一篇正文发到不同平台，**不是复制粘贴，也不是重写一遍**——是「同一批事实，换一套讲法和包装」。

> ## 通用规范在哪（先读它，再读本文）
>
> 多平台改写的通用规则——改写铁律（可以变的 / 绝对不能变的）、声道与平台的关系、
> 总流程七步、**7 张平台卡片**（读者场景 / 声道 / 标题 / 开头 / 结构 / 篇幅 / 专属件 / 禁忌）、
> 写回契约、交付前自查、常见坑——**唯一真源是**：
>
> **`~/.workbuddy/skills/content-factory-kit/references/platforms.md`**
> （技能 `content-factory-kit` 支路 A；本技能原来的 `references/platforms.md` 是它的子集，已删除并入）
>
> 本文只写两样：**本机数值口径**（套件里刻意抽象成「越短越好」的那些具体数字）、**本机写回契约**。

## 何时使用

- 多平台类动作：`juejin`（掘金版本）`xhs`（小红书版本）`sumsocial`（4 平台摘要）
  `adapt`（平台适配）`shortvideo`（短视频脚本）`vid60`（60 秒脚本）
- 手动要求「把这篇改成 XX 平台版本」
- 发布前判断某个平台版本是否可直接发

不适用：原稿写作与改稿（走 `content-writing-spec`）、封面与配图（走 `content-visual-spec`）、
研究（走 `content-research-spec`）。

## 一、本机数值口径（套件里被抽象掉的具体数字，以这里为准）

套件的平台卡片刻意写「以平台当前提示为准、不写死上限」，所以数字口径落在本层：

| 平台 | 本机口径 |
|---|---|
| 微信公众号 | 标题**两段式 25–35 字**、留悬念不剧透；**摘要 ≤100 字**且不剧透结论；**朋友圈转发语 ≤40 字、第一人称**；正文 1500–2500 字（起稿 ≤2400，与 `content-writing-spec` 同一口径） |
| 掘金 | 标题技术向、不用情绪词、**给 3 个备选**；**摘要 ≤120 字**，讲清解决了什么问题；**标签 ≤5 个**；正文 2000–4000 字 |
| CSDN | 标题可带技术关键词、不必强行两段式；篇幅不限、**宁长勿短** |
| 小红书 | 标题 **≤20 字**、真实语气不标题党；**首图文字 ≤10 字**；正文 **300–600 字**、每段不超 2 行；**标签 8 个**（大流量词 + 精准长尾词混合） |
| 视频号 | **60–120 秒**稿（约 **200–400 字**口播文字）；封面文案短且**不含品牌元素** |
| B站 | **3–10 分钟**稿；章节分节 + 结尾三连引导 |
| 抖音 | **15–60 秒**稿；**句子不超过 15 字**；一条只讲一个论点 |

> 这些数字会随平台调整，**发布前仍以平台当前提示为准**；本表是写作时的目标区间。

## 二、本机写回契约

多平台类动作的落点字段统一是内容主表的**制作方案**（不是正文——原稿不会被覆盖）：

```bash
export PATH="/usr/bin:/bin:/mingw64/bin:$PATH"
printf '%s' "$TOKEN" | python3 tools/queue.py --token-stdin done <任务ID> --summary "一句话" --value "$(cat 平台版本.txt)"
```

- **`done --value` 是覆盖写**：如果一个内容的制作方案里已经有封面方案、插图方案，
  再写多平台版本会**把它们顶掉**。
- 所以多平台写回时，**先在任务卡里读「已有正文 / 制作方案」**，用**追加式排版**写，
  保留并接续已有内容的结构，不要只输出自己这一段。
- 长文一律 `--value "$(cat 文件)"`，别直接内联。

## 三、本机自查增量（套件那份 8 条之外）

- 各平台字数是不是落在**本层 §一**那张表的区间里？
- 制作方案里原有的封面 / 插图方案有没有被顶掉？
- 结果摘要里列清「生成了哪几个平台版本 / 各自字数 / 落在制作方案」。
